expensive to search. This is the *index*: one line per fact, with a status. A

is how the same ground gets covered twice — and a shortest-path search with no
visited set is not a shortest-path search.

## Status vocabulary (revised 2026-08-18)

The old EST/OUT/WD tags hid *how* something was known. Roughly a dozen entries
were wrong this session, and they did **not** fail for lack of evidence — every
one cited real evidence, correctly gathered. They failed because the **claim was
broader than the evidence supporting it**. So the tag now records the kind of
support, because the kinds have very different reliability.

| tag | meaning | track record |
|---|---|---|
| **INTERVENED** | Changed one input, watched the symptom move. | **Never wrong yet.** Strongest available. |
| **MEASURED** | A tool reported this value. The claim is the *literal* reading, nothing more. | **Never wrong yet.** |
| **READ** | What the code says. Good for "what does this do"; **not** evidence about what actually runs. | Reliable when kept to behaviour-in-principle. |

## Rules for this file

1. **A claim is established only if a test ran that could have contradicted it
   and didn't.** A grep returning nothing usually could not have. A watchpoint
   held across the whole failure window could — but only with a positive control
   showing the same tool fires elsewhere.
2. **Every negative names its scope inside the claim.** Not "nothing calls this"
   but "nothing in splat's asm calls this". This rule alone would have prevented
   a third of our errors, including the day we declared a working probe broken.
3. **Load-bearing claims** — anything a fix or a decision will rest on — carry
   **Observed / Falsifier / Checked**. Everything else stays one line; full
   rigour on every entry is unaffordable.
4. **Distinguish the number from its meaning.** "CALLBACK=0" is MEASURED; "the
   list was empty" is INFERRED. Record them as separate claims or not at all.
5. An entry that gets overturned becomes **WD** — never deleted. The overturned
   belief is exactly what a future session would otherwise re-derive.
6. Add the entry when the finding lands, not at session end.
7. **Write it SHORT — the median entry is ~124 words and carries claim, status,
   evidence and falsifier fine.** `check_ledger.py` names every entry over 250
   words on each edit. That is a warning, not a gate: some entries earn their
   length. The point is that length becomes a decision instead of an accident,
   which is all it was on 2026-08-19 (**T51**).
8. **When a roll supersedes an entry's framing, COMPRESS the old text to one
   line — do not push it down under "Prior text follows".** Superseded framings
   must survive, because they stop resurrections (rule 5), but one line does
   that as well as a paragraph. Entries here are internally append-only by
   habit, and A99 had accumulated four full layers before anyone noticed.
   **This, not retained history, is what makes the file grow:** the
   2026-08-18 entries average 112 words, the 2026-08-19 entries 398 (T51).
9. **Archiving is the opposite discipline — be lazy about it.** It needs
   hindsight, since only later do you know what turned out to be load-bearing,
   and both archivable investigations are already done (T46).
   **Strict at write time, lazy at cut time.**
10. **Merging two entries that record the same lesson is allowed, and it is the
    only edit here that destroys structure rather than prose. So:**
    * **Never delete the merged-away ID.** It stays as a stub reading
      `MERGED into <ID>`, so every existing citation resolves and the visited
      set is preserved. `check_ledger.py` enforces that the target exists.
    * **Every instance keeps its own identity, fix and control** — one line
      each. "It happened five times" is the evidence; a merge that blurs the
      instances into one story throws away the reason to believe it.
    * **If the entries disagree, say which rule wins, in the class entry.**
      T20 and T22 both gave a run-count rule and T20's was superseded; a reader
      hitting T20 first was getting wrong guidance. **That, not size, is what
      merging is for** (T53).
    * **Do not merge on resemblance.** T16, T23 and T37 sit next to merged
      entries and were deliberately kept separate — see T53 for why, and do not
      re-merge them.

## Load-bearing claims — full treatment

These are the claims decisions rest on. Each states what was *literally*
observed, what would falsify it, and whether that was checked.

### L1 — The START crash was a truncated symbol (fix applied)
- **Claim (MEASURED + INTERVENED):** `ovlfile02_func_800E4F34` was declared
  `size = 0x14`; the real function is `0x8C`. The generated C stopped after the
  first call, dropping the registration of the renderer's per-frame reset.
- **Observed:** generated C for that address contained 5 instructions ending at
  a `jal`; m2c of the same address emits 35 statements. splat's own `endlabel`
  and the next symbol both put the end at `0x800E4FC0`.
- **Falsifier:** the generated C containing the later statements, or splat
  agreeing with `0x14`, or the crash surviving the size correction.
- **Checked:** yes, all three. After the fix the missing registrations appear in
  a probe log and a 2h36m user-confirmed run never crashed (was 100% reliable).

### L2 — The attract freeze and the START stall are ONE bug
- **Claim (INTERVENED):** both are thread 4's stack overflowing onto the
  dispatch table at `0x8007AF0C`.
- **Observed:** a watchpoint caught `boot_func_800489C0` — a 4x4 matrix multiply
  that stages 16 floats on its own stack frame — writing the float `0.0463` over
  the function pointer. With `SNP_STACK_RELOC=4` graphics run through the START
  transition to 848 tasks at +30/s; without it the identical run stalls at ~360.
- **Falsifier:** the workaround failing to change the START symptom, or the
  clobbering write coming from somewhere other than thread 4's stack.
- **Checked:** yes. This is an intervention, which is why it is trusted.

### L3 — Thread 4's dispatch slots are NULLed at the stall
- **Claim (MEASURED):** `D_8007AF0C` and `D_8007AF10` hold valid addresses for
  12 samples, then read `0x00000000` for every sample to end of run.
- **Observed:** exactly that, via `SNP_WATCH` on both words.
- **Falsifier:** either slot holding a valid address after the stall.
- **Checked:** yes. **But note:** `func_80026598` legitimately calls
  `func_8004D500(0)`, so a NULL is not *by itself* proof of corruption — the
  corruption evidence is L2's float write, not this.

### L4 — The scene-graph data does not change during the failure
- **Claim (MEASURED, negative with a control):** neither the cycle node's child
  array (`0x8010273C`) nor the pointer to it (`0x8010278C`) is written between
  t=35s and t=62s, spanning the entire failure.
- **Observed:** two hardware watchpoints, zero hits.
- **Falsifier:** either watchpoint firing.
- **Checked:** yes — and the **positive control** is that the same tool fired
  immediately in its two other uses this session. Without that control these
  would be worthless non-results.

### L5 — The recursion genuinely gets deeper
- **Claim (MEASURED):** thread 4's stack low-water falls from `0x8007B748` to
  `0x8007AFE8` — 1,880 extra bytes — landing 220 bytes above the word L2 shows
  being clobbered.
- **Observed:** `low_sp` is an observed minimum stack pointer, not a tally, so
  it cannot be inflated by a miscounting loop.
- **Falsifier:** low_sp staying flat while the level counter rose (which would
  indict the counter instead).
- **Checked:** yes — the two moved together, so the depth growth is real even
  though the **`cycles=81` attribution remains unverified** (that detector has
  been wrong once already, see I2).

### L6 — splat's asm is not the whole ROM
- **Claim (MEASURED):** splat covers `0x80020000-0x8005FFFF` and `0x800E0000+`
  only; `0x80060000-0x800DFFFF` (620 functions) is absent — 5,853 `glabel`s vs
  6,827 recompiled functions.
- **Observed:** per-64KB histogram of `glabel` addresses, plus a symbol count.
- **Falsifier:** finding any `glabel` in the missing range.
- **Checked:** yes. **This is the rule-2 lesson:** two entries asserting
  "nothing in the ROM does X" were really "nothing in splat's asm does X", and
  both were wrong. Use `RecompiledFuncs/` for any completeness claim.

### L7 — The attract freeze was a truncated symbol (fix applied, user-confirmed)
- **Claim (MEASURED + INTERVENED):** `ovlfile20_func_800E5634` was declared
  `size = 0x54`; the real function is `0x118`. The generated C stopped before the
  epilogue, so the function allocated `0x18` of stack per call and never restored
  it — once per frame, until the stack walked onto the dispatch table at
  `0x8007AF0C`.
- **Observed:** generated C with `addiu $sp, $sp, -0x18` and **no restore and no
  `jr $ra`**, while control demonstrably returned to the dispatch loop. Corrected
  to `0x118`, the C gains `+0x18` at `0x800E5740` and `jr $ra` at `0x800E5744`,
  ending exactly on the next symbol `0x800E574C`.
- **Falsifier:** the drift surviving the size correction, or `fmax` still
  descending in the fixed build, or the freeze still occurring at gfx 1240.
- **Checked:** yes, all three, 3 isolated runs per arm. Baseline `fmax` descends
  `0x8073EA90 -> 0x8073CC30/0x8073CC78`; fixed `fmax` is flat across all three.
  On the real 8KB stack with no `SNP_STACK_RELOC`: gfx `2651 / 2649 / 2651` at
  `+30/s`, against a freeze at 1240. **User-confirmed on screen 2026-08-18:** the
  attract demo ran to the END of the video (t=146s, gfx 4349) with no input,
  where it previously froze at t~41s.
- **Note:** second instance of L1's class (BC-2). Both were found by the same
  signature — generated C with no epilogue. That is a sweepable pattern.

### L8 — The VI thread dereferences a null `ViState::mode` when the game autostarts (upstream PR 1)
- **Claim (INTERVENED):** with the `next_mode == nullptr` guard reverted, the VI
  thread SIGSEGVs within 3s of launch; with it applied, the VI thread never
  faults. This is a bug in **upstream** `N64ModernRuntime`, not in our port.
- **Observed:** 3 isolated runs per arm, the arms differing **only** by the
  10-line patch. The build is **bit-reproducible**, so each arm was confirmed by
  SHA-256 rather than assumed: reverted `6c44917297bcc06c…`, patched
  `21a6e7251e4284af…`, and the reverted rebuild reproduced the previous
  session's reverted binary byte-for-byte. **Reverted:** SIGSEGV at **2s / 2s /
  3s**, `VERDICT=CRASHED`, 15-line logs ending at font/asset init with **zero**
  game output. gdb on that build: `Thread 54 "VI Thread" … vi_thread_func()`,
  `si_addr = 0x1c`, faulting instruction `mov 0x1c(%r15),%edx` with `%r15` = 0;
  `0x1c` is `OSViMode::comRegs.hStart` (3 bytes padding + `type`, `ctrl` at 4).
  **Patched:** 3 runs, VI thread never faults, `+30/s` sustained to t=156.
- **Falsifier:** the reverted arm surviving its first VI iterations; the patched
  arm faulting in `vi_thread_func()`; or the reverted crash turning out to be an
  artifact of our own instrumentation.
- **Checked:** yes, all three. A 4th reverted run with `SNP_HEARTBEAT` **unset**
  also died at 3s, excluding our probe threads as the timing cause. The probe
  patch adds 724 lines to `events.cpp`, but all of it sits **after**
  `osViGetCurrentFramebuffer`; `update_vi` / `vi_thread_func` / `set_dummy_vi`
  are byte-identical to upstream apart from the fix.
- **CONTROL DESIGN — the trap this nearly fell into:** **both arms crash.** The
  patched arm still dies at ~158s on the unrelated A99 title-screen walker bug.
  A crash/no-crash reading of this experiment concludes the patch does nothing.
  The control only works because it discriminates on **time and faulting
  thread** — 2-3s in `vi_thread_func` vs 158s in the scene walker on thread 3.
- **Mechanism, READ against upstream `589bbf0` (0 behind), not inferred:**
  `ViState::mode` has no initializer while its sibling `retrace_count = 1` does,
  and `events_context` is static, so `mode` is a deterministic `nullptr`.
  `set_dummy_vi()` — the only thing that populates it pre-`osViSetMode` — is
  called **only** inside `if (!is_game_started())`, while `update_vi()`
  dereferences unconditionally a few lines later. `is_game_started()` is
  `game_status.load() != None` and `recomp::start_game()` stores `Running`
  directly, with no dependency on the game's MIPS code reaching `osViSetMode`.
  `update_vi()` ends `*get_next_state() = *get_cur_state()`, so **one** pre-start
  `set_dummy_vi()` populates both slots permanently — hence a first-iteration
  race only, which `SP_AUTOSTART=1` makes near-certain.
